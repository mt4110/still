# still の週次整理と Before／After の設計

## 目指す体験

SSD の使用率を見て、前週から増えた場所を開き、候補の容量・根拠・削除後の影響を確認する。選んだ対象の処理後に、実測した空き容量と残存物を確認できる。週次の繰り返しで、調査にかかる手間を減らす。

今回の実装範囲は日本語 UI、右上のヘルプ、文字と操作アイコン、Mac のディスク統計、Docker 内の容量一覧、フォルダ走査の進捗。既存のプロジェクト別一覧・週次差分・確認後の削除・実測結果につなげる。Library の読み取り専用照合と観測履歴の実装範囲を末尾に示す。

## Library の候補を作るアルゴリズム

1. ホーム内の対象を段階的に集計する。`Caches`、`Logs`、`Application Support`、`Containers`、`Group Containers` の直下で容量を把握し、詳しい調査を選んだ場所へ進む。シンボリックリンクをたどらず、読み取り不可・共有領域・別ボリュームを記録する。
2. 所有元を照合する。既知の bundle ID、アプリの登録情報、既知のフォルダ構造、App Group の対応を利用する。インストール確認・実行中・現在使用中・アンインストールを確認済み・所有元未確認を別々に記録する。アプリ名に似たフォルダ名だけでは所有元を確定しない。
3. 日時を確認する。配下で得られた更新・作成・アクセスの最新日時と、週次観測の増減を保持する。ディレクトリ自体の更新日時と配下の活動を区別する。アクセス日時の欠落や未対応も表示する。
4. データの用途を分類する。再生成可能なキャッシュ、再取得可能な SDK、診断ログ、作業履歴、永続 DB、未同期データ、共有データに分類し、根拠と削除後の影響を示す。用途を確認できない項目は未確認として表示する。
5. 候補を並べる。まず容量と前回からの増加で調査先を示す。所有元・利用状況・日時・データ種別を組み合わせ、確認できた根拠を行ごとに表示する。削除できるもの、個別確認が必要なもの、保留理由があるものを明示する。
6. 実行直前に照合する。既存の選択済みツリー照合、Git 追跡、リンク、開いているファイル、Docker のマウント保護を再利用する。選択後の変更は再確認につなげる。

| 観測した状態 | 提案する内容 | 確認する影響 |
| --- | --- | --- |
| 再生成可能なキャッシュで、対象アプリが閉じている | 容量と再生成元を示して選択へ進める | 次の起動やビルドが遅くなる可能性 |
| アプリのアンインストールを確認済みで、古いキャッシュが残っている | 所有元の確認方法と最後に観測した活動を示す | 再インストール時のキャッシュ再作成 |
| インストールが見つからず、古いフォルダだけ残っている | 所有元未確認として調査を提案する | 別名アプリ、CLI、共有データとの関連 |
| Slack・Teams のログや作業履歴が大きい | 容量・期間・保存先を示す | 証跡や障害調査で必要な期間 |
| Notion などの DB・未同期データが大きい | アプリ内の管理方法と保存データを確認する | オフラインデータ、未同期の編集、復旧方法 |
| Docker の未参照ボリュームが大きい | 名前・参照数・容量・接続元を示す | コンテナを止めた後も残す永続データ |
| 複数アプリが使う領域、所有元不明、現在使用中 | 具体的な保留理由を表示する | 利用元と更新・停止状態の再確認 |

候補の説明は「対象アプリのアンインストールを確認」「配下の活動を180日間観測していない」「再生成元を確認」のように、確認した事実から組み立てる。未取得の情報は未確認と示す。端末内のルールと観測で動作させる。

## Before／After の記録

- Before は同じボリュームの空き容量、選択した対象、論理容量・割当量、所有元、根拠、保持対象を固定する。
- 実行結果は対象ごとに削除済み・一部残存・保留・確認不能を保持する。Xcode のように管理一覧から外れてもイメージが残る場合は、その根拠と容量を残す。
- After は同じボリュームの空き容量を再測定し、選択対象の残存を再確認する。全体の空き容量差と対象の観測サイズをそれぞれ表示する。
- APFS の共有ブロック・スナップショット・遅延解放、Docker 仮想ディスク、同時に動くアプリの影響を結果の解釈に含める。処理直後と再確認時の結果を区別する。
- 週次履歴には増えた場所、実行した操作、保留の理由、回収の実測値を保存する。履歴は端末内に保持する。

## 製品として追加したい提案

### 増えた場所から始める

ホームに前回の整理後から増えた上位フォルダを表示する。プロジェクト、アプリ、Docker を共通の入口から開けるようにし、毎週同じ全一覧を探す手間を減らす。

### 再生成の負担も選択材料にする

容量と一緒に、再ビルド、再ダウンロード、アプリの初回起動などの影響を示す。手動の「残す」を端末内に保存し、プロジェクトや版ごとに次回の候補へ反映する。負担の時間は観測できた場合に示す。

### 残った理由まで解決する

一部残存・保留から、残存場所、使用中のプロセス、管理ツール、再確認へ進めるようにする。確認不能だった項目を後から再確認できる状態で残す。

### 毎週の少ない操作で評価する

本人の MacBook で、起動から候補確認までの操作数、調査にかかる時間、理由を理解できた割合、意図したデータの保持、回収の実測を確認する。ホーム、候補一覧、確認画面、結果画面を同じ手順で試して改善する。

## 次の実装の区切り

1. Library の容量と所有元を読み取り専用で一覧化する。アプリを残したケースと、アンインストール後の試験データを使い、誤った所有元の推定を確認する。
2. 週次観測・日時・利用元から候補の理由を組み立て、保持設定を導入する。古い DB、共有コンテナ、未同期データ、仕事のログを含めて表示を試す。
3. 再生成元が確認できたキャッシュの処理を既存の選択・確認・実測フローへ接続する。対象・影響・復旧方法を表示し、選択した分に処理を限定する。
4. Developer ID 署名・公証済みの配布物で、別端末と利用先のセキュリティ製品を確認する。Windows の署名・Store 配布も各 OS の実際の経路で確認する。

### 実装済みの観測範囲

Library 直下の対象5領域を明示スキャンし、同じファイルシステム上の割当容量と、通常ファイルの更新・作成・アクセス記録の最新値を集計する。フォルダ自体の更新日時も別に扱う。ファイル本文は読まない。共有コンテナ以外でディレクトリ名と登録済みアプリの bundle ID が完全一致したときだけ、対応するアプリと起動中かどうかを照合する。未登録、登録照会失敗、アンインストール確認済みは同一視しない。アクセス記録の古さは未使用の証明にしない。

通常ファイルの名前から DB・ログ・アーカイブ・バックアップ形式の可能性を集計する。名前だけの手掛かりであり、内容・用途・削除可能性を確定しない。本人が特定の bundle ID についてアンインストールと場所の確認を申告した場合は、選択した確認範囲・日時とともに端末内に記録し、撤回・再確認できる。OSの証明や削除判断には使わない。

App Group は、利用者が明示的に選んだアプリ一つの署名と entitlements を調べ、指定したグループIDの宣言との完全一致を確認できる。署名の整合性は発行元の真正性や利用状況、すべての利用元の証明ではなく、同時変更も完全には検出できない。共有コンテナの所有元を自動確定したり、照合結果を削除判断に使ったりしない。

デスクトップの明示スキャンで直前の完全観測との差を表示する。ワークスペースと Library で「残す」を選んだ場所は、次回の確認と削除直前に照合する。

明示したワークスペース調査では、各時点のルート全体の論理容量・割当容量・部分調査の状態を端末内に記録し、Mac の操作メニューまたは `still review-history` で履歴を確認できる。フォルダごとの過去全件は保存せず、この機能の追加前の観測も遡って作らない。掃除履歴には、取得できたスキャン時の割当容量、開始時のワークスペースの保持設定、元のパスを確認した時刻を記録する。

SDK、Docker コンテナ、Docker ビルドキャッシュの操作も、対象・結果・測定できた空き容量を整理履歴に残す。SDK の一部残存や確認不能を区別し、残存イメージの容量を確認できた場合は併記する。Docker の生出力や接続先詳細、エラーの原文は保存しない。

ホームでは、プロジェクトの増加に加えて、比較可能な Library の増加と Docker の種類別容量差を別々の根拠・観測日時で示す。Docker は同じ daemon・接続先・バージョンなどの条件を満たす場合に限り、丸められた Docker の集計値を比較する。共有領域を含むカテゴリを合計せず、Mac の空き容量差とも区別する。未取得や失敗は画面に示す。

最初の Library 整理対象は Google Chrome の Default プロファイルの HTTP キャッシュ。登録済みの bundle ID と停止状態を確認し、固定された保存先で Chromium の索引とエントリの形式を照合する。対象と再取得の影響を表示し、承認されたディレクトリだけを再検証してステージに移す。完了または未完了の理由とボリュームの空き容量差は既存の整理履歴に記録する。ログ、DB、共有コンテナは読み取り専用とする。

配布検証では macOS のローカル署名付きバンドルに加え、Windows CI で検証用 ID の MSIX を作成し、展開した CLI と GUI のハッシュを release ビルドと照合する。Developer ID 署名・Apple 公証・別端末での確認と、この版の Store 署名・実機確認は外部配布の工程として残る。
