# still

[README_EN](./README_EN.md) 

**ローカルストレージの容量調査と開発生成物の掃除**

容量順のツリーを開いて調査し、生成物やマージ済みワークツリー、Docker 資産を確認できます。削除は選択した対象を明示的に確認してから実行します。

## 特徴
- **容量順の探索と再帰検索**: 指定したディレクトリを Rust で並列走査します。
- **Library の隔離**: 保管庫（Vault）へ移した項目を復元できます。
- **ローカル優先**: GitHub の PR 照合は `--github-pr` を指定した時に実行します。

## プライバシー

**still はユーザーデータや利用状況を開発元に送信しません。テレメトリー、利用分析、クラッシュレポートの自動送信はありません。** スキャン結果は端末内で処理します。週次プロファイルや比較用の履歴も端末内に保存します。

**「Find old files…」と `still stale` の検索範囲は、自分のホームフォルダ（`~/`）内だけです。** 既定の **Home (~)** で **Scan** を押すと、フォルダを個別に選ばずに調べられます。OS の権限に従って走査し、読み取れなかった項目数を結果に表示します。ファイル本文は読み込まず、パス・サイズ・日時などを確認します。隠し項目、`Library`、`node_modules` は対象外で、シンボリックリンクやジャンクションをたどりません。

Mac ではワークスペース調査もホーム内に限ります。保存済みプロファイルや CLI でも、`/`、`/tmp`、`/nix/store` などホーム外のフォルダは指定できません。Windows のワークスペース調査は指定したフォルダを使います。`still review` でフォルダを省略した場合は、コマンドを実行したディレクトリが対象です。

macOS の「ファイルとフォルダ」の許可は、デスクトップ、書類、ダウンロードなどの場所ごとに管理されます。普段の調査を開発フォルダに絞るには、**Choose folder…** で `~/_workspace` などを選べます。

Docker と Kubernetes の調査は指定したローカルの接続先を使い、`--github-pr` を指定した場合は `gh` で GitHub に照会します。

## インストール

```bash
# Nixを使用する場合
nix develop
cargo build --release

# 通常のCargo
cargo install --path .
```

### デスクトップアプリ（macOS / Windows）

初期表示は日本語です。Mac は左下、Windows は右上の言語メニューで英語にも切り替えられます。**ヘルプ** は、候補の調べ方、保留理由、削除確認、権限とプライバシーをアプリ内で説明します。

Mac のサイドバーの **ディスク** では、ホームフォルダがあるボリュームの使用率と空き容量、その物理ディスクの読み込み・書き込み速度を確認できます。この画面を開いている間に約2秒間隔で計測します。**Docker** では、現在のローカル接続先、または指定した接続先のコンテナ・イメージ・ボリューム・ビルドキャッシュを容量順に表示します。名前・ID・状態で絞り込み、行を選ぶと参照数やマウントなどの詳細を確認できます。Docker 内のサイズは、SSD の実際の回収量と異なる場合があります。

Mac の Docker 画面で明示的に調査した後、Docker の `version`、`info`、`system df` を読み取り専用で追加実行し、種類別の容量サマリーを端末内に追記します。接続先・daemon・Dockerの版・保存方式とカテゴリが一致する観測だけを比較し、概要画面に種類ごとの概算の増減を表示します。Dockerの表示値は丸められ、種類間で容量が重なる場合があります。足し合わせた容量やSSDの回収量として扱いません。接続名・日時・カテゴリ別サイズ・比較結果と比較用の識別子を保存し、daemon IDとソケットパスはハッシュ化します。観測履歴は自動削除しません。取得や保存に失敗した場合は画面に表示します。

Mac は左のナビゲーションから各画面を開き、候補一覧の右側で判定理由と削除後の影響を確認できます。保留や保護の項目も名前と容量を読みやすく表示し、選択した分だけ確認画面に進みます。選択とホバーの色は短く変化し、macOS の「視差効果を減らす」が有効なら起動時に動きを抑えます。画面構成と状態の扱いは [デスクトップの UX](docs/DESKTOP_UX.md) にまとめています。

フォルダ調査中は、確認済みのファイル数・フォルダ数・論理容量・調査している場所を表示します。容量の集計後は、掃除候補の安全性確認へ切り替わります。Library の残り物の所有元推定と週次提案、Before／After の記録は [整理アルゴリズムと製品プラン](docs/CLEANUP_STRATEGY.md) にまとめています。

macOS では `still.app`、Windows ではスタートメニューの `stilll` から開きます。Mac は **調査先とプロファイル → 調査フォルダを追加…**、Windows は **その他の操作 → 調査フォルダを追加…** で調査先を選び、プロジェクトごとの容量と候補を確認します。フォルダ探索では容量順の表示とパスの再帰検索を利用できます。**別名で保存…** で週次プロファイルを保存できます。CLI の `still review --save-profile` で保存したプロファイルも開けます。

**Cleanup candidates** で候補のサイズと理由を確認します。チェックを付けて **Review … selected** を押すと対象の詳細が開き、最終確認の **Delete selected** を押したときだけ、選んだ生成物を削除します。削除はゴミ箱を経由しません。**Candidate sources** で再生成できる専用出力先、Git リポジトリ、ローカル Docker 接続先を追加できます。Git と Docker の候補はアプリで調査できます。Mac の Docker 画面ではコンテナを選択・確認して削除できます。Git とその他の Docker 資産の削除は専用 CLI で確認して行います。

候補が多いときはパスで絞り、**Select all eligible** で表示条件に合う候補をまとめて選べます。親子の候補は親にまとめます。**Scan … selected** は選択分を読み取り専用で調べ、**Review … selected → Delete selected** で最終確認したフォルダを最大2件ずつ削除します。候補一覧を操作中は10秒おきに表示行の存在を確かめます。Mac では現在地のパスの各階層や選択した行から Finder を開けます。**Find old files…** の結果は容量順・更新日の古い順・作成日の古い順に切り替えられます。

Mac ではホームの「_workspace を調べる」から開始できます。直下のフォルダをプロジェクトとして、使用量・候補容量・前回比を一覧表示します。プロジェクトを開くと、個別の生成物の説明、保留理由、「Finder で開く」と「この項目を再確認」が表示されます。初回の走査が比較の基準になります。

概要の「容量の大きい場所を探す」では、ホーム、システム領域、または選んだフォルダを読み取り専用で走査できます。フォルダは容量順に並び、クリックで中に入り、上のフォルダやパスの表示から戻れます。別ボリュームは走査せず、権限のない項目も読めません。外付けボリュームはフォルダ選択から個別に調べてください。

アプリの保存容量画面では、必要に応じて Library の主要な保存先の調査を選べます。CLI では `still app-storage --library` です。`Caches`、`Logs`、`Application Support`、`Containers`、`Group Containers` の直下にあるフォルダを読み取り専用で集計します。ファイル名からDB・ログ・アーカイブ・バックアップに見える件数を示しますが、本文は読まず、内容や用途を確定しません。判別できない名前や未調査の項目はその旨を表示します。所有元・用途は未確認として表示し、リンクはたどりません。既知の保存先と重なる行があるため、表示容量を合算できません。

Macでは、Library行のフォルダ名から認識できるbundle IDについて、自分がアプリをアンインストールし確認した場所（`/Applications`、`~/Applications`、または両方）と時刻を端末内に記録できます。本人の申告であり、OSやstillによる証明ではありません。記録は更新・撤回でき、削除可否や自動選択には使いません。別の場所やユーザーは確認範囲に含まれません。

標準の Cargo `target` が保留になった場合、`debug`・`release` 直下の `incremental` と `deps` は個別に検査します。Cargo の痕跡と中身の形式を確認できたフォルダだけが選択でき、証明書・ログ・結果など判別できない項目を含むフォルダは保留になります。

別の場所に置いた Cargo 出力も、ビルド痕跡が揃えば表示します。対応するプロジェクトが確認できない場合や、Git 追跡ファイル・リンク・保護項目などがある場合は、一覧の **Status** に保留理由が出ます。削除時には内容の変化や使用中のファイルを再確認します。
言語メニューで、画面や保留理由を英語・日本語に切り替えられます。行をクリックすると、長いパスを含む理由の全文が出ます。

**Find old files…** で、ホーム配下から更新・アクセス・作成のうち、取得できた最新の日時が指定の日数より古いファイルを容量順に探せます。対象フォルダや最小サイズを指定して、結果をパスで絞れます。画面ではCLIと同じく既定で開発プロジェクトの生成物を含め、チェックを外すと確認できた生成物を除外します。画面では使用中かどうかは確認しません。ターミナルの `still stale --older-than-days 180 --min-mib 512` は上位候補の使用中チェックを試みます。`--root` でホーム配下のフォルダを指定できます。開いているプロセスが見つからなくても、不要とは限りません。隠し項目、`Library`、`node_modules` はどちらも走査対象外です。

```sh
# ソースからウィンドウを起動（macOS / Windows）
cargo run --locked --features desktop --bin still-desktop

# macOS のローカル配布用 .app
cargo build --locked --release --features desktop --bins
scripts/build-macos-app.sh target/release/still target/release/still-desktop 0.3.0 target/still.app
```

別の Apple Silicon Mac に渡すときは、`still.app` を ZIP にまとめて転送し、展開したアプリを「アプリケーション」に入れます。転送先で Rust や Nix をインストールする必要はありません。週次プロファイルは端末ごとのパスを使うため、転送先で **Add workspace… → Save as…** から作成します。

```sh
ditto -c -k --sequesterRsrc --keepParent target/still.app target/still-macos-arm64.zip
```

PR の **Rust CI → build (macos-15)** が成功すると、実行結果の **Artifacts → still-macos-arm64** からアプリの ZIP を取得できます。既定のローカル作成版と CI 作成版は自己利用向けのアドホック署名で、公証は行っていません。

組織管理の Mac 向けには、キーチェーンにある **Developer ID Application** 証明書を明示して署名し、Apple の公証を受けた ZIP を用意できます。`Apple Development` 証明書はこの配布用の指定に使えません。

```sh
STILL_SIGNING_IDENTITY='Developer ID Application: Your Name (TEAMID)' \
  scripts/build-macos-app.sh target/release/still target/release/still-desktop 0.3.0 target/still-signed.app
scripts/notarize-macos-app.sh target/still-signed.app still-notary target/still-notarized.zip
```

`still-notary` は、利用者が `notarytool` に登録済みのキーチェーンプロファイル名です。公証スクリプトはアプリのコピーを Apple に提出し、承認、チケット添付、Gatekeeper の検証が成功した場合に配布 ZIP を作成します。既存の入力アプリや出力ファイルは上書きしません。組織のセキュリティ製品には、その組織の許可設定が追加で必要な場合があります。[Apple の Developer ID](https://developer.apple.com/developer-id/)、[公証の公式ガイド](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

Windows の MSIX は [パッケージ作成スクリプト](scripts/build-windows-msix.ps1) に両方の実行ファイルを渡します。Smart App Control がオンの PC には、Microsoft Store が署名したパッケージを使用します。

### アプリと SDK の容量（Mac）

**App storage…** で、Android NDK の版ごとの容量、Unity Asset Store のダウンロード済みパッケージ、Unreal Engine のローカル DDC、ブラウザのキャッシュ、Slack・Teams のログ、Notion のローカルデータを確認できます。既知のホーム内の場所を対象に容量だけを調べ、ログやデータベースの本文には触れません。Xcode のインストール済みランタイムは、チェックを入れた場合に Xcode の一覧を取得します。

CLI では `still app-storage`、Xcode の一覧も含めるなら `still app-storage --xcode-runtimes` を実行します。CLI は読み取り専用です。Mac アプリでは、Chrome を終了してから「既定プロファイルの HTTP キャッシュを確認…」を選べます。対象は Google Chrome の Default プロファイルの `Cache_Data` のみです。確認画面には容量・件数・再取得の影響が表示され、実行結果は `still cleanup-history` に残ります。「Library の整理で残す」は次回の調査にも反映されます。SDK の版は各管理ツールで利用状況を確認してください。Notion のローカルデータや仕事の証跡になりうるログは保護表示します。ワークスペース調査では Unity の元アセットとキャッシュ、Unreal Engine 本体、元アセット、自動保存、ログ、生成キャッシュも判別して表示します。

「アプリと SDK の容量」では、明示的に選んだアプリ1つの署名付き App Group 宣言を、入力したIDと照合できます。CLI は `still group-link --app <アプリの絶対パス> --group <App Group ID>` です。署名の整合性は発行元の真正性を証明せず、選んだアプリ以外の利用元、所有元、使用中かどうかも分かりません。同時変更をすべて検出できる保証はありません。宣言を確認できない場合は未確認として扱い、照合によってデータは削除しません。

Mac 版の **App storage… → Review Xcode & NDK versions…** では、版ごとの容量と候補／保護の理由を表示します。古いランタイムは最終利用記録、端末の状態、テスト設定を確認し、利用記録がある場合は45日を目安にします。プロジェクト設定と NDK のビルド記録は、開いているプロファイルのフォルダ、`~/_workspace`、`~/AndroidStudioProjects` を調べます。候補を選んで **Review … selected → Uninstall … selected** と進むと、再確認できた版だけを各管理ツールでアンインストールします。結果には Mac のデータボリュームの前後の空き容量と、実測した差が出ます。

Xcode の削除処理後は、利用可能ランタイムの一覧と、対象ビルドのイメージも照合します。残っている場合は **一部残存** と表示し、確認できたイメージの使用量を、データボリューム全体で実測した空き容量の差と別に示します。

## 使い方：3ステップ・ワークフロー

### 開発ディレクトリの容量調査と掃除

```sh
# 容量を調べる
still review --root ~/_workspace

# 指定した開発ルートで生成物の掃除も有効にする
still review --cleanup-root ~/_workspace

# 独自スクリプト専用の出力先を登録する
still review --cleanup-root ~/_workspace --output ~/_workspace/my-project/generated

# 再帰検索を構造化出力で取得する
still review --root ~/_workspace --search .next --format json
```

毎週同じ範囲を見たい場合は、初回にプロファイルを保存します。

```sh
still review --save-profile weekly --cleanup-root ~/_workspace
still review --profile weekly
```
`--root` だけで保存すると容量調査用のプロファイルになります。初回は比較元を記録し、次回から差分を表示します。差分の `*` は一部を走査できなかったときの観測値です。`--format json` などのレポート出力は走査履歴を更新しません。

記録されたワークスペース全体の容量推移は、Macアプリのワークスペース操作メニューにある「この場所の容量履歴…」または `still review-history --root <絶対パス>` で確認できます。CLI の週次プロファイルで記録した場合は `--profile <名前>` を追加します。各観測の論理容量、取得できた割当容量と一部未走査の有無を表示し、CLIでは `--format json` と `--limit` も指定できます。古い最新比較用データから、それ以前の履歴は復元しません。履歴は端末内に観測ごとに保存し、自動削除しないため、スキャンを重ねると件数が増えます。

`Enter` でディレクトリを開き、`←` で親に戻ります。`/` で現在地以下を検索し、`o` で別の調査先を開きます。`s` で合計容量順、最大ファイル順、前回からの増加順を切り替えます。増加順はプロファイルの前回走査があるときに使えます。

`Tab` に Cargo、Next.js、Vite の生成物候補と、対応するソースがある CPython のバイトコードキャッシュが出ます。`package.json` の隣の `node_modules` も容量を表示しますが、ローカル変更やリンクを含む可能性があるため削除対象にはしません。`Space` で選ぶと、Git の追跡状態と配下のファイルを確認します。`D` で実際に削除する対象を確認し、`y` で実行します。削除はゴミ箱を経由しません。`--output` は再生成できる専用出力先に指定してください。Unity の `Library` は容量と保護理由を表示します。

選択後に変更を検出した出力や、リンク・保護対象を含む出力は保留されます。選択・実行時は通常ファイルの内容も読み、変更を照合します。内容は保存・送信しませんが、大きな出力の確認には時間とディスク読み取りが必要です。照合はすべての同時変更を防ぐ保証ではありません。エラーで `.still-stage-*` が残った場合、`original-path.txt` が元の場所、`payload` が残ったデータです。空き容量の増減はストレージ全体の観測値です。

`--git-repo` に元の Git チェックアウトを指定すると、同じ候補画面にリンク済みワークツリーと判定理由が出ます。既定の比較先はローカルの `main` です。取得済みのリモート追跡ブランチを使うなら `--git-base refs/remotes/origin/main` を指定します。

Rust の差分コンパイル用キャッシュ全体が保留でも、完了したコンパイル単位を個別に選べます。未完了の作業域・用途不明のファイル・保護マーカーがある単位は保持し、選択後の変更や使用中のファイルは実行前に再確認します。

残存ステージ内のデータを戻す場合は、Mac アプリの **残ったステージを確認… → 復元を確認** から Finder で内容と表示された移動先を確認してください。CLI では `still stage-cleanup <ステージのパス> --cleanup-root <対象ルート>` で確認し、同じ指定に `--restore` を加えると残存する `payload` を記録された元の場所へ移動します。既存の移動先は上書きしません。ステージの記録は由来や完全性の証明ではなく、処理中に一部が削除済みの場合があります。復元後もステージの記録は残ります。

デスクトップの生成物削除結果は、対象パス・結果・論理容量とボリュームの空き容量の前後値を端末内に記録します。取得できた場合は、削除前のスキャン時の割当容量、開始時にそのワークスペースに適用される「残す」設定、元のパスの存在を確認した時刻も記録します。MacではSDKのアンインストール、Dockerコンテナとビルドキャッシュの整理結果も記録します。部分残存・未確認は成功と区別し、Dockerの生出力や接続先詳細は保存しません。`still cleanup-history` または `still cleanup-history --format json` で参照でき、保存失敗は結果画面に表示します。削除が未完了の場合、元のパスが残っていなくてもステージ領域に残っている可能性があります。

Macで一部残存と表示されたときは、再スキャン後にワークスペースのメニューから「残ったステージを確認…」を開きます。場所を選ぶと内容を検査し、空のフォルダ・認識できたFinderメタデータ・元の場所の記録だけであれば、確認画面から片付けられます。CLIでは `still stage-cleanup --cleanup-root <整理ルート> <ステージのパス>` が確認のみ、同じ指定に `--apply` を付けると削除します。

「アプリと SDK」→「アプリの保存容量」でLibraryを選ぶと、保存先の分類、配下のファイルで観測した最新日時、前回の調査からの容量差を確認できます。フォルダ名が登録済みアプリのbundle IDと正確に一致した場合は、そのアプリの場所と観測できた起動状態を表示します。共有コンテナや対応を確認できなかった場所は確認専用です。プロフィール・履歴・Vaultは従来の保存先を使います。


`--docker-context colima` を指定すると、同じ画面で Docker の候補を確認できます。BuildKit は `--docker-cache` で調査します。指定した接続先のコンテナの bind mount と重なる出力は保護します。候補画面の `f`、`g`、`d` はファイル、Git、Docker への移動です。回収量は観測値からの目安で、Docker の表示は Docker 内の容量です。Git と Docker の削除には、それぞれ `still worktrees` と `still docker` を使います。各オプションは `--save-profile` で保存できます。

### マージ済み Git ワークツリー

```sh
still worktrees --repo ~/projects/app --root ~/projects/app-worktrees
still worktrees --repo ~/projects/app --root ~/projects/app-worktrees \\
  --base refs/remotes/origin/main --github-pr 42
still worktrees --repo ~/projects/app --root ~/projects/app-worktrees \\
  --remove ~/projects/app-worktrees/task-done
```

`--base` の既定はローカルの `refs/heads/main` です。`--github-pr` は `gh` を使って `origin` の PR を照合します。削除時も、確認したときと同じ `--base` と `--github-pr` を指定してください。未コミット・未追跡・ignored ファイルのあるワークツリーは保留されます。生成物だけを掃除するときは `still review` を使えます。Codex が管理するワークツリーの全体削除は、そのチャットの管理画面から行います。

### Mac アプリでのコンテナ整理

**Docker** 画面でスキャンし、最終停止日時・作成日時の古い順、または容量順に並べ替えられます。名前・ID・状態・イメージの検索、状態と経過日数のフィルターを組み合わせ、チェックボックスで選択してください。「表示中の候補を選択」は、現在表示されている選択可能なコンテナだけを対象にします。検索・フィルターの変更時は選択を解除します。

「選択した項目を確認」で接続先・完全な ID・理由・日時を再確認し、確認画面の削除ボタンを押した分だけ削除します。実行中、保持指定、管理対象、詳細不明などは理由付きで選択できません。削除前にも接続先と状態を再取得します。コンテナの強制削除は行わず、マウント先・ボリューム・イメージは保持します。**コンテナの書込データと Docker 管理ログは失われ、ゴミ箱には入りません。**

ビルドキャッシュ画面では、未使用期間を指定して接続先の既定ビルダーのキャッシュをまとめて整理できます。確認画面で対象の接続先・期間・影響を表示し、実行直前に接続先とデーモンを再確認します。対象の全件や回収量は事前に確定できません。次回のビルドが遅くなるほか、キャッシュマウントのデータが失われる可能性があります。イメージとボリュームの画面は調査用です。

日時は直近の起動・停止・作成の観測値です。完全な利用履歴やログを保存する必要性は判断できず、「古い＝不要」とは扱いません。結果画面は各件の成功／保留と、Mac の実測空き容量差を表示します。書込層の見込み容量と実際の SSD 回収量は別です。VM のディスク内で空いても、Mac の空き容量にすぐ反映されるとは限りません。

### Docker の掃除候補

```sh
still docker --context colima --include-cache
still docker --context colima --remove 'image:sha256:表示された完全なID'
```

停止中も含むコンテナから参照されていない、取得元の digest があるイメージを表示します。一時用途のコンテナは作成時の `still.disposable=true` ラベルで識別します。`--include-cache` はローカルの組み込みビルダーの古いキャッシュを表示します。削除は表示された個別 ID を対象にします。サイズは Docker 内の値です。

未参照ボリュームはデータが残る可能性があるため、保護状態として表示します。

### ローカル Kubernetes / K3s

```sh
still kube --kubeconfig ~/kube-local.yaml --context my-local --namespace dev
```

終了済み Job と Pod を読み取り専用で確認できます。終了から7日以上経過し、`still.disposable=true` ラベルがある成功済みリソースがレビュー対象です。失敗済みやコントローラー管理下のリソースは保護理由を表示します。デスクトップの **Candidate sources**、または `still review` の `--kubeconfig`、`--kube-context`、`--kube-namespace` でも追加できます。接続先は TLS を検証できるループバックの API に限定されます。

### Library の既存ワークフロー

安全にクリーンアップを行うための基本的な3ステップです。

### 1. Scan (スキャン)
ディスクをスキャンし、削除・隔離候補を洗い出して「計画ファイル (`plan.json`)」を作成します。この段階ではファイルは一切変更されません。

```bash
# デフォルト（安全なセット）でスキャン
still scan

# スコープ一覧を確認
still scan --list-scopes
```

Windowsでは、除外ルールの照合が曖昧になるのを避けるため、走査先・ルール範囲・globに `RUNNER~1` のような既知の8.3形式に見える表記があるとスキャンを中止します。長い名前を指定してください。同形の通常名やglobも拒否する場合があり、すべての8.3形式を検出できる保証はありません。大文字小文字や他の別名、ジャンクションを使った異なる表記の同一性も解決しません。

### 2. Review (確認・選別)
作成された計画ファイルをTUIで開き、アイテムごとにアクションを決定します。推奨アクションは表示用で、初期状態ではすべて Keep です。

```bash
still tui
```

- **操作**:
    - `j` / `k`: 移動
    - `Space`: アクション切り替え (Keep -> Quarantine -> Trash)
    - `b`: バルクモード（まとめて変更）
    - `q`: 保存して終了

### 3. Apply (適用)
TUIで決定したアクション（隔離やゴミ箱への移動）を一括で実行します。

```bash
still apply
```

- **Quarantine (隔離)**: `~/Library/Application Support/still/vault` に移動されます。後で復元可能です。
- **Trash (ゴミ箱)**: macOSのシステムゴミ箱へ移動されます。
- **Keep**: 何もしません。

### 保管庫の管理 (Vault)
隔離（Quarantine）されたアイテムを管理します。

```bash
# 隔離アイテムの一覧
still vault list

# アイテムの復元
still vault restore <ID>

# 期限切れアイテムの完全削除（ディスクから消去）
still vault purge --expired
```
